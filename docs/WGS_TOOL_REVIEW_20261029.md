# WGS: инструменты и узкие места — 29.10.2026

## 1. Проверенный программный стек

Актуальное содержимое `WGS_GATK_simple/envs/wgs.yaml` после перехода с BWA на BWA-MEM3:

| Этап | В окружении | Доступная более новая версия | Что делать |
|---|---|---|---|
| Alignment | BWA-MEM3 0.15.1 | 0.15.1 (Bioconda) | Оставить основным aligner; индексировать на compute-node |
| BAM/CRAM | samtools 1.24 | 1.25 (официальный сайт HTSlib) | Пока оставить 1.24: проверить зависимости Bioconda |
| VCF/BCF | bcftools 1.24 | 1.25 | Перейти позднее, отдельным коммитом |
| Calling | GATK 4.6.2.0 | 4.7.0.0 | Кандидат на следующий контролируемый апгрейд |
| FASTQ QC/trim | fastp 0.24.0 | 1.3.7 | Возможен апгрейд; влияние лишь при `trim_fastq: true` |
| Depth QC | mosdepth 0.3.11 | 0.3.14 | Поддержка CRAM 3.1 и исправления, а не доказанное ускорение |
| QC report | MultiQC 1.30 | 1.35 | Можно обновить для улучшения отчётов; не ускоряет calling |

Указанные версии проверены по официальным релизам и страницам проектов.
Это **не означает**, что все новые версии совместимы между собой в одном Conda-окружении.
В частности, BWA-MEM3 0.15.1 для некоторых сборок зависит от HTSlib 1.24,
поэтому обновлять samtools/bcftools на 1.25 следует только после успешного
`conda create --dry-run` или в изолированной тестовой среде.

## 2. Альтернативы, но **не** drop-in replacements

**BCFtools mpileup + call**: простой, хорошо автоматизируемый вариант для
быстрого SNP calling и непосредственного multisample calling. При этом
вычисление генотипов и качество variant calls могут заметно отличаться от
GATK HaplotypeCaller в сложных участках/indels. Лучшее место — отдельный
экспериментальный backend, а не тихая замена текущих gVCF.

**Strelka2**: в сравнениях WGS может быть существенно быстрее GATK HC,
но её схема подготовки данных и joint calling отличаются. Нельзя просто
заменить бинарник в `haplotypecaller.sh` и оставить GATK GenomicsDB.

**DeepVariant + GLnexus**: потенциально конкурентный путь; DeepVariant
имеет быстрые реализации inference, а GLnexus масштабирует совместное
генотипирование gVCF. Нужно проверять переносимость модели с человека на
белух/белых медведей и доступность CPU/GPU; текущий анализ не доказывает
повышение точности на этих видах.

**FastDup / Sambamba / biobambam2**: возможные ускорители duplicate marking.
Сравнения FastDup с Picard/Sambamba не являются доказательством ускорения
относительно используемого нами `samtools markdup`. Замена изменит метрики
дубликатов, поэтому сначала требуется сопоставление на одном BAM.

**NVIDIA Parabricks**: GPU-ускорение нескольких вариантов FASTQ→VCF.
Для CPU-only SLURM-кластера неприменимо без подходящих GPU и проверки
условий лицензии/развёртывания.

Источники:
- https://snparcher.github.io/explanation/variant-calling/
- https://github.com/google/deepvariant/releases
- https://academic.oup.com/bioinformatics/article/41/12/btaf633/8362221
- https://docs.nvidia.com/clara/parabricks/about-parabricks
- https://academic.oup.com/bib/article/26/6/bbaf652/8374034

## 3. Где сейчас вероятнее всего теряется время

1. **Alignment:** в сохранённом отчёте SLURM от 26.10 два `WGS_align`
   выполнялись 42 852 и 51 336 секунд (11 ч 54 мин и 14 ч 16 мин).
   Это измерения старого BWA 0.7.18, а не BWA-MEM3. Приоритет —
   правильные индексы и запуск новой версии.
2. **SLURM stage barriers:** этапы объединяются в массивы, зависимость
   `afterok` ставится на *весь массив* предыдущей стадии. Следующая стадия
   не может начать работу, пока не завершатся последние задачи предыдущей.
   Улучшение зависимостей потенциально сократит общее время обработки,
   но это изменение планировщика и механизма возобновления, а не смена тулов.
3. **HaplotypeCaller:** генотипы вызываются отдельно на каждый contig и
   каждый образец. Это удобно для повторного использования gVCF, но
   порождает много задач и накладные расходы JVM/SLURM. Размер задач и
   число одновременных JVM следует выбирать по фактическим log/SLURM.
4. **Storage:** выравнивание использует временные файлы samtools sort,
   прежде всего локальный `$SLURM_TMPDIR`, а при его отсутствии каталог
   выходного BAM. I/O на общей FS может стать ограничением; пока не измерено.

Сохранённый `slurm_baseline.tsv` не содержит `TotalCPU`/`MaxRSS`, поэтому
точную загрузку CPU и реальное потребление памяти для этих заданий по нему
рассчитать невозможно. Достаточно дополнить `sacct` этими полями при
следующем штатном расчёте.

## 4. Порядок действий

- **Сейчас:** BWA-MEM3 0.15.1, существующие стадии samtools/GATK;
  использовать подготовленный минимальный рефакторинг Python/Bash.
- **Следующий безопасный этап:** обновлять GATK, fastp, mosdepth и MultiQC
  по одному с проверкой unit/CLI, версий и изменившихся outputs.
  Не объявлять ускорением само обновление версии.
- **После появления штатных BAM/GVCF:** оценить расход CPU/RAM/I/O и
  задержки SLURM; только потом менять job-array scheduling или caller.
- **Позднее:** вынести сравнение альтернативных calling-backend в отдельное
  исследование, не усложняя основной pipeline до получения данных.

Критерий любого рефакторинга: сохранение интерфейса, сигнатур задач (кроме
явно изменившихся зависимостей), научных команд, имён outputs и структуры
checkpoint. Изменение `validate_alignment.py` **намеренно меняет** сигнатуры
`import` для BAM/CRAM, так как её содержимое включено в хеш задач. В данном
патче эта проверка стала короче, но проверяет те же свойства заголовков.
