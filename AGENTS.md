# Правила разработки — Minimal SNP Panels (Beluga & Polar Bear)

## 1. Цель проекта

Проект состоит из двух независимых вычислительных конвейеров:

1. **Подготовка WGS:** FASTQ или готовый BAM/CRAM → выравнивание, QC, variant calling, joint genotyping → VCF/BCF для каждого вида.
2. **Основной конвейер SNP-панелей:** готовые VCF/BCF + `population_labels.tsv` → QC → статистики по популяциям → ранжирование SNP → фильтрация по LD → панели разного размера → классификация и корректная кросс-валидация → минимальная панель при заданном пороге качества (если достижим).

Основной конвейер должен уметь работать **без запуска и установки WGS-конвейера**. Получение или уточнение популяционных меток по полногеномным данным относится к отдельному исследовательскому анализу, а не к обязательному пути исполнения основного конвейера.

## 2. Текущий приоритет

**Сейчас:** (1) рефакторинг имеющегося `WGS_GATK_simple` для понятности без изменения научного поведения; (2) измеримое ускорение **только после baseline**, отдельными изменениями с измерением производительности и регрессионными тестами; (3) зафиксировать интерфейс WGS → VCF/BCF и оставить изолированные заглушки будущего анализа популяционной структуры/отбора SNP.

**Не сейчас:** полноценная реализация PCA/ADMIXTURE/кластеризации, SNP-ranking, LD-фильтрации для панелей, классификации и nested CV; спекулятивные ускорения без профилирования.

Критерий успеха — биоинформатик без знакомства с историей проекта может открыть README, понять структуру, запустить проверки, найти нужный этап и изменить его без изучения всего проекта.

## 3. Правила проектирования

- **KISS, YAGNI, Separation of Concerns** важнее архитектурной изощрённости.
- Использовать функции, модули и `dataclass` там, где они повышают ясность. Не вводить абстрактные фабрики, плагины, собственный workflow-engine или лишние классы без подтверждённой необходимости.
- Одна понятная ответственность на модуль; главная функция показывает последовательность этапов на высоком уровне.
- Явные имена (`sample_id`, `reference_fasta`, `output_vcf`), явные входы/выходы и типы для публичных функций. Не передавать магические словари через весь код, когда формат можно определить единожды.
- Значения по умолчанию и валидацию настроек хранить централизованно.
- Научные команды BWA, samtools, GATK, bcftools остаются в `scripts/stages/*.sh`, а Python отвечает за конфигурацию, план и исполнение.
- Комментировать **почему** принято нетривиальное решение, документировать входы/выходы функций; не комментировать очевидные присваивания.
- Меньше файлов и зависимостей — при равной понятности. Модуль выделять, только если это устраняет смешение обязанностей.
- Поддерживать Ruff (Python), pytest, ShellCheck и единое форматирование Bash; применение форматтеров не должно незаметно менять научные команды.

## 4. Строгие ограничения для текущего рефакторинга WGS

Без отдельного изменения ТЗ и тестов НЕ менять:

- пользовательские команды: `./run.sh validate|plan|local|submit|status` и служебную `run-task`;
- формат `config.yaml` и `samples.tsv`, принятые FASTQ/BAM/CRAM;
- порядок этапов, граф зависимостей и правила SLURM job arrays;
- параметры научных команд и версии/наименования применяемых инструментов;
- выходные файлы, их содержимое, расположение и соглашения об именах;
- правила проверки завершённости, контрольных отметок (`checkpoints`), сигнатур и повторного запуска;
- поддержку двух видов, нескольких FASTQ-дорожек, 21 аутосомы белухи и 36 аутосом медведя в текущих конфигурациях.

Не объединять WGS и будущую SNP-панель в один зависимый граф, не добавлять обязательную загрузку WGS, не делать `population_labels.tsv` входом WGS.

Изменения поведения и исправления ошибок оформлять отдельным коммитом/PR с тестом, объяснением и оценкой совместимости. Работающие расчёты и текущие результаты не трогать.

**Важно:** в текущей реализации сигнатуры задач зависят в том числе от байтов Bash-скриптов стадии. Даже изменения комментариев в них могут привести к повторному выполнению стадий. Изменения сначала проверять в отдельном `workdir`.

## 5. Контракт будущего SNP-пайплайна (зафиксировать, но пока не реализовывать)

- Входы: один или несколько совместимых VCF/BCF по одному виду и одной сборке референса; отдельный TSV с обязательными полями `sample` и `population`.
- Каждый анализ выполняется отдельно по виду. ID образцов в метаданных должны сопоставляться с именами образцов в VCF/BCF. Несоответствия, дубликаты, неоднозначный порядок/представление вариантов должны выявляться явно.
- Пользователь задаёт размеры исследуемых панелей и/или целевую метрику с порогом (например, `balanced_accuracy >= 0.95`). Если порог не достигнут, нужно сообщить это, а не выдавать произвольную панель как удовлетворяющую требованиям.
- Результаты: QC, статистики и ранжирование SNP, кандидатные панели, результаты классификации, CV-метрики, confusion matrices, качество по размерам, выбранная панель и воспроизводимые настройки.
- `population_labels.tsv` — вход основного модуля. Отдельные PCA/кластеризация и обоснование меток могут использовать WGS, но не становятся обязательной зависимостью.
- Любые шаги, оцениваемые по данным и способные повлиять на выбор SNP (включая фильтрацию по частотам/LD, ранжирование, настройку классификатора и подбор размера панели), должны выполняться **внутри обучающей части каждого CV-разбиения** при оценке качества. Внешняя оценка и финальная модель должны быть отделены.
- Если метки получены кластеризацией тех же генотипов, высокая точность воспроизведения этих меток **не является независимым подтверждением реальных биогеографических популяций**; это ограничение должно быть отражено в отчёте.
- Требуемая точность должна быть привязана к конкретной метрике и процедуре валидации; «минимальная» означает минимальную **среди проверенных размеров/кандидатов**, а не гарантированный математический глобальный минимум.

## 6. Приёмка каждого шага рефакторинга

1. Предъявить короткое описание прежней проблемы и нового упрощения.
2. Подготовить тесты **до** изменения кода; сохранить эталонные планы для FASTQ (с trim и без), BAM, CRAM, нескольких дорожек, обоих видов.
3. Сравнить до/после: состав и порядок логических задач, `id`, `stage`, `deps`, `inputs`, `outputs`, команды (`body`), конфигурацию SLURM, поведение `resume`; при изменении сигнатур выяснить причину и влияние на повторный запуск.
4. Выполнить `pytest`, `python -m compileall`, `bash -n`, Ruff/ShellCheck по возможности.
5. Не запускать WGS, `submit` и большие вычисления без прямого указания пользователя.
6. В ответе дать изменённые файлы, описание изменений, конкретные результаты тестов и непроверенные сценарии.

## 7. Производительность: оптимизировать уже сейчас, но только по данным

1. Снять/прочитать текущие результаты SLURM (`sacct`) и зафиксировать commit, конфигурацию, версии, время, память, CPU efficiency и I/O по стадиям.
2. **Безопасные изменения** (рефакторинг Python, отсутствие повторного сканирования метаданных, не создавать лишние промежуточные файлы) проверять планами и регрессиями.
3. **Потенциально меняющие поведение изменения** (число потоков, структура SLURM массивов, команды, параметры GATK/bwa/samtools, I/O, форматы файлов) выносить в отдельный PR с контрольными расчётами на малых данных и сравнением результата.
4. Не менять действующий `workdir` и проверочные отметки у уже запущенных задач; измерять только в отдельном тестовом каталоге.
5. Отчёт об ускорении содержит абсолютное время, CPU·h, пик RAM и коэффициент ускорения для сравнимых нагрузок; не выдавать изменение конфигурации за доказанное ускорение.

Приложен `benchmarks/summarize_sacct.py` для offline-первичного анализа SLURM-отчётов; он не запускает задачи.

## 8. Порядок текущей работы

1. Тестовый baseline и схема существующего WGS.
2. Простые, явные типы данных и небольшие функции построения этапов.
3. Разделение `workflow.py` (план) и `pipeline.py` (исполнение/SLURM) только там, где это реально упрощает код.
4. Документация WGS и контракт VCF/BCF + population labels.
5. Добавить самостоятельную, не вызываемую WGS заглушку `population_structure/`, которая принимает VCF/BCF и только формирует план будущих исследований, **не создавая фиктивных population labels**.
6. Анализ производительности по существующему baseline, затем прицельные оптимизации отдельно от рефакторинга.
7. Реализовать `snp_panel/` после стабилизации WGS и согласования научных методов.
