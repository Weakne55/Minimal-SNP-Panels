# Инструкция для сопровождающего

## Где искать нужную часть

| Если нужно… | Откройте… |
|---|---|
| Поменять входные WGS, пути к референсам | `config/samples.tsv`, `config/config.yaml` |
| Понять, какой софт выполняет стадию | соответствующий `scripts/stages/*.sh` |
| Поменять состав задач или их порядок | `scripts/workflow.py` |
| Поменять правила возобновления работы и SLURM | `scripts/pipeline.py` |
| Поменять формат таблицы входных данных | `scripts/model.py` |
| Узнать реальные команды упавшей задачи | `workdir/jobs/scripts/TASK_ID.sh` |
| Узнать причину ошибки | `workdir/jobs/logs/*.err` / `*.out` |

## Типовые ситуации

**Новый образец.** Добавить строку в `samples.tsv`, затем `./run.sh validate`, `./run.sh plan`, `./run.sh submit`. Совместное генотипирование на тех же контигах пересчитается с обновлённым списком образцов. Не обновлять таблицу или план, пока в очереди ещё есть задания прежнего запуска.

**Сбой узла.** Посмотреть `sacct` и файл лога (`jobs/logs`). Проверить свободное место и память. Исправить причину и снова запустить `./run.sh submit`; `--force` обычно не требуется.

**Мало памяти / слишком мало времени.** Поменять `slurm.resources.STAGE.mem_mb` или `hours` в `config/config.yaml`, затем повторно отправить. Обратите внимание, что Java `-Xmx` настраивается отдельно в `gatk.*_heap_gb` и должен быть меньше RAM, выдаваемой SLURM.

**Нужно пересчитать всё.** Выполнить `./run.sh submit --force` **только когда нет активных старых задач**. Это может потребовать значительного диска и времени.

**Сменился референс.** Используйте **новый workdir** и пересоздайте индексы BWA/samtools/GATK для нового FASTA. Нельзя смешивать BAM/GVCF/VCF разных сборок.

**Референсные contigs.** В списке должны быть только нужные названия, точно соответствующие `.fai`. Выбор одной хромосомы не ограничивает FASTA до этой хромосомы — HaplotypeCaller запускается с `-L` для выбранного контига.

## Что делать перед передачей проекта

1. Провести локальные тесты `python3 -m pytest -q` и `bash -n ...`.
2. Настроить `config/config.yaml` и реальную таблицу `config/samples.tsv` **на стороне получателя**.
3. Проверить environment, reference indexes, права на входные файлы, доступ к SLURM и место на диске.
4. Выполнить `validate` и `plan` на реальной когорте.
5. Сделать один маленький end-to-end запуск FASTQ -> VCF и проверить число образцов, порядок контигов, индексы VCF, QC и логи.
6. Зафиксировать commit/version репозитория, версии программ и использованные команды запуска в отчёте.

## Ограничения, которые нельзя скрывать

- Результат — **сырой**, а не отфильтрованный VCF; downstream QC обязательна.
- Markdup сделан только для FASTQ-пути; поданные извне BAM/CRAM должны быть подготовлены заранее.
- Для одной пробы поддерживается одна библиотека FASTQ с несколькими lane; несколько библиотек требуют отдельного решения по duplicate marking.
- Референсы и их индексы готовятся до запуска.
- Конвейер не обеспечивает автоматический подбор памяти под размер WGS; эти значения корректируются по ресурсам кластера.
- Структурные тесты не гарантируют совместимость инструментов, версий ядра, файловой системы и очереди SLURM; нужен реальный прогон.
- Обработка по отдельным хромосомам может потребовать много временного пространства для GenomicsDB.
- **Dockerfile отсутствовал в исходном архиве** и не включён в этот рефакторинг: до передачи, если он обязателен по ТЗ, его нужно добавить и протестировать отдельно.
